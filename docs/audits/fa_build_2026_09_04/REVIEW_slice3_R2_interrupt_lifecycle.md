## Findings

### 1. P1 — Two of the three first-step attack arms still drop the whole battle, including the capture prompt
**Seam:** `backend/commands/strategic_executor.py::_execute_strategic_command` — the co-located PURSUE arm and the move-failed-at-target PURSUE arm. Both now READ `attack_was_refused` (the slice's refusal half) and then fold only `combat_msg` into `first_step_msg`; the final return is the generic order dict. FA-N42/N48's `_carry_combat_fields` was applied to `_handle_first_step_blocked`'s aggressive arm only.
**Repro:** `Ney, pursue Mack` with Ney adjacent (boot geometry) or co-located: Mack DESTROYED, the reply has `events: []`, no `battle_report`, no `battle_diorama`. Probe 8 (Ney at Franconia, Mack 3k at Austrian Bohemia): the advance CAPTURED Bohemia, `world.pending_capture_choice = {"region":"Bohemia","capturer":"Ney",…}`, the reply's key subset was `['events']` with `events: []`; the next command `Davout, hold` → `success: False`, "You must decide how to handle the captured region first!" (that refusal is what finally carries `pending_capture_choice`/`capture_data`, so the modal appears one swallowed command late — the IGR-X7 shape).
**Client effect:** `main.gd::_display_result` sees no battle event → plain green line; no battle header, no Berthier report, no "View the field" link, no diorama stash, no plunder/secure modal.
**Fix sketch:** in both arms keep the attack result and, at the final return, `_carry_combat_fields(ret, attack_result)` — the same discipline as the fixed aggressive arm; pin with the probe-8 geometry (a capture, not just a kill).

### 2. P2 — The per-turn seam of FA-N48 is not closed: a HARD STOP staged by an end-turn strategic battle reaches the wire only inside `battle_details`
**Seam:** `strategic.py::_handle_combat_result` victory row (`**carry` only — `_combat_carry` returns `battle_report/battle_details/battle_message`; the triad stays nested in `battle_details`), and `main.py::_apply_command_popup_contract` (enemy-phase branch never attaches the manager's current dialogue).
**Repro:** Ney MOVE_TO Nassau issued last turn, Mack 3k on Hesse-held Nassau, cannon fire suppressed. `end turn` → row `Ney defeats Mack! Continuing.`; `battle_details` has `diplomatic_dialogue.type == war_purpose_selection`, `war_purpose_popup`, `battle_diorama`; top-level `diplomatic_dialogue: None`. World: `pending_diplomatic_dialogue.type == war_purpose_selection` (current). Next command `Davout, status` → `success: False` "Our purpose in this war awaits your answer, Sire — nothing was relayed…"; next `end turn` → the same refusal; `current_turn` stays 2.
**Client effect:** no renderer reads `battle_details`, so the question is invisible until the first command of the new turn is eaten; the PT-A3 refusal carries the dialogue, so it is one swallowed command per occurrence rather than a lockout — but the popup then arrives with no battle context.
**Fix sketch:** lift the triad onto the row in `_combat_carry` AND promote a current `war_purpose_selection` to the end-turn response; the client must STASH it when `enemy_phase` is present and raise it from `_return_control_to_player` (the `_post_hud_response_routes` table runs before the enemy-phase branch in `_on_command_result`, which is why the backend defers today — attaching it raw would skip the report).

### 5. P3 — The flipped contract opens a client hole: a first answer that resolves into a follow-on popup orphans the rest of the queue for the turn
**Seam:** `main.gd::_on_interrupt_response`: `_route_response_ui(response, _post_hud_response_routes)` returns before `_process_next_interrupt()`; `_process_next_interrupt` has only that caller plus the null-popup fallback; `_on_capture_choice_response` never calls it; `interrupt_queue` is next cleared by `_on_strategic_report_dismissed`.
**Reachable now because** the slice carries `pending_capture_choice`/`capture_data` and the war-purpose triad on the answer arm: marshal A's `attack` captures or stages a war purpose → capture/proposal_confirm route → B's queued question is never popped that turn. Under the old one-question-per-turn pin this was unreachable. Nothing is lost (B's stored question is re-emitted by step 0a), but B stands idle a turn and is asked a turn late.
**Fix sketch:** chain `_process_next_interrupt()` from the capture / charge / proposal-confirm dismissal tails (or route them all through one control-return tail that drains `interrupt_queue` before re-enabling input).
