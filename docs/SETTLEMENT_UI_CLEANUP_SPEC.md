## Purpose

The Imperial Settlement / Common Peace feature reached normal UI paths, but the Slice F closeout exposed a product-quality gap: some settlement controls are technically wired while not delivering the player action their labels promise. This spec is a cleanup gate before Slice G or any broader settlement agency work.

The opening blocker is `Revise Terms`: the button currently routes through typed dialogue plumbing and reopens the same review, but it does not open an editor or change the draft package. A player-facing `Revise Terms` action that cannot revise terms is not complete.

The broader blocker is now explicit: the common-peace UI currently behaves like a one-button white-peace lever while displaying settlement, terms, acceptance, pressure, and revision affordances that imply a richer treaty system. The approved product direction is the full treaty-settlement path: the player must be able to author, preview, negotiate/revise, and ratify concrete treaty terms. Temporary hiding/removal is still allowed to protect the player from broken affordances while this is implemented, but the cleanup target is not a permanent white-peace rebrand.

This spec exists to find and close every adjacent gap of the same class. The desired end state is not a technically reachable popup; it is a settlement flow a player can use, understand, revise where promised, be refused when acceptance fails, and trust.

- Button exists, but does not perform the player-visible action.
- UI path exists, but falls back to typed command text, generic mailbox text, or nation-picker recovery.
- Payload fields exist, but player surfaces still omit the reason, beneficiary, ignored party, stale-state cause, or remaining-war context.
- Tests assert source strings or schema fragments while missing the behavior a player actually uses.

## Non-Negotiable Rule

No settlement UI slice is complete because a route exists. It is complete only when the player-facing surface does the named action, shows the necessary state to understand the outcome, and has behavioral coverage that would fail if the action became a no-op.

Settlement ratification must respect the same acceptance verdict and hard stops the review surface advertises. A popup that displays `Acceptance: 12 / 50 - Unlikely` or a red `HARD_STOP` warning and then ratifies anyway fails this spec unless the product explicitly rebrands the feature as a non-consensual diktat and removes misleading acceptance language.

Common peace must not pretend to be a treaty-settlement system while only supporting an empty/no-clause package. The approved target is real treaty authoring: draft clauses, preview acceptance and political consequences, revise/counter terms, preserve incoming-offer packages, and revalidate before mutation. Until those parts are implemented, incomplete controls must be hidden or omitted rather than shipped as visible promises. Disabled placeholder buttons for unavailable settlement systems are forbidden because they still read like promised player agency. `available_clause_types[]` plus `clause_control_schema` are the source of truth for clause visibility: if a type is absent from those backend-authored structures, no client may render it as a greyed-out or disabled label.

Deferral policy:

- A visible broken or misleading settlement behavior cannot be deferred silently.
- A defer decision must name the player impact, hide or remove the broken affordance when possible, and be explicitly accepted in status/spec text before coding proceeds.
- Every interim hide must record four artifacts before code starts: owning SC row, restoring implementation slice, `docs/STATUS.md` tracking line, and a CI/test gate that fails if the owning slice closes while the affordance remains hidden.
- No deferred settlement affordance may point at an unnamed row or vague backlog. It must appear in the Deferred Work Landing Ledger below with an owning SC row, a landing slice, a completion definition, and at least one behavior test that fails if the landing slice closes while the work is still absent.
- The landing ledger is not a waiver. It is the backlog contract for player-facing work that is hidden during cleanup. A ledger item can leave the backlog only by shipping the named behavior and tests, or by a recorded product decision in this spec and `docs/STATUS.md` that removes the player-facing promise from the game entirely.
- If there is a conflict between finishing quickly and making the settlement feature actually usable, choose quality.

## Scope

Included:

- `settlement_confirm` actions and presentation.
- Common-peace entry from diplomacy wizard, war detail, coalition detail, notification rail, dispatch, and ledger.
- Incoming AI settlement-offer no-exposure cleanup; positive review and response actions only if SC-5 is explicitly reversed with producer, payload, UI, voice, and behavior tests.
- Settlement stale-state recovery, route focus, and result feedback.
- One-to-one war settlement affordances versus bilateral peace / armistice.
- Tests that claim UI routing or button behavior is covered.

Out of cleanup visible scope, but not unowned:

- Full Slice G AI treaty authorship, ally petitions, conference mechanics, or veto systems are assigned to SC-32 and Slice G2 in the Deferred Work Landing Ledger.
- New settlement term economics unless needed to make an existing button truthful.
- Broad redesign of the diplomacy wizard outside settlement actions.

## Known Blocker: Revise Terms

Current behavior:

- `revise_settlement_terms` returns a typed backend response with `must_reopen=True`, `reopen_target`, unchanged `settlement_terms`, and `mutated=False`.
- Godot now avoids command-box fallback and reopens the settlement review by calling the normal war-settlement entry path.
- That entry path re-stages from scratch and does not preserve or mutate draft terms.
- Godot's reopen call currently forwards only `war_id` and `target_nation`; even if the backend returns `settlement_terms`, `_on_war_settlement_clicked(...)` drops them and sends a fresh `propose_common_peace` request.
- No term editor, draft-package builder, or term mutation surface is opened.

Root-cause diagnosis:

- The original Slice F closeout treated "no command-box fallback" as the Revise Terms fix. That solved the wrong layer: the button stopped synthesizing typed text, but still had no editor, no draft mutation, and no terms-preserving route.
- The interim safety decision then hid `Revise Terms` rather than rendering it disabled. That was valid for SC-2 in isolation, but it created the rejected-popup dead end once `Ratify Settlement` became unavailable: the only available player action became `Back Out`.
- Tests pinned the presence/absence and backend response shape around ratification and revise handling, but no behavior test asserted the player-facing rejected-popup action set. A rejected `settlement_confirm` payload with no real recovery route therefore passed.
- Future fixes must test the whole popup contract, not only the individual button contract: when ratification is blocked, the payload must provide at least one honest next-step affordance or an explicit, approved temporary no-next-step deferral with player impact recorded in `docs/STATUS.md`.

Required cleanup decision:

- Either implement a real term revision flow, or remove/hide the button until such a flow exists.
- Renaming to `Review Again` is acceptable only if the action remains a review-only loop and the product wants that loop.
- Keeping the label `Revise Terms` without an editor fails this spec.

Minimum acceptable fix:

- `settlement_confirm` must not expose `Revise Terms` unless the payload declares an actual editable draft flow, such as `can_edit_terms=true` plus a concrete route target.
- Tests must fail if `Revise Terms` appears without an edit-capable route.

Full fix:

- Add a settlement draft editor reachable from `settlement_confirm`.
- Preserve `war_id`, accepting leader, proposer side, covered enemies, draft terms, and route metadata.
- Re-preview acceptance and warnings after draft changes before ratification.
- Confirm still revalidates live state and never mutates from stale preview data.

## Critical Synthesis

These are the non-deferrable product issues for the cleanup gate:

1. The common-peace player path currently opens and ratifies an empty/no-clause package unless external code passes `settlement_terms`. The approved fix is draft term authoring with real preview/revision/ratification flow. This is the root P0 because it makes every term, harshness, projection, and revision affordance suspect.
2. `Revise Terms` and incoming-offer `Request Revision` are false revision affordances until a real editor or negotiation route exists.
3. `Ratify Settlement` must not mutate state when the displayed acceptance verdict rejects the proposal or when hard stops exist.
4. `incoming_settlement_offer` is registered and handler-tested, but current code comments state there is no gameplay producer. Handler scaffolding is not shipped offer functionality.
5. Multi-war and coalition settlement entry points must preserve the exact war context instead of guessing, choosing a sorted first war, dead-ending, or routing the player to a generic ledger/popup.
6. Typed/free-text settlement entry is part of the same route-safety contract as the wizard: when no `war_id` is supplied and multiple shared wars exist, it must reject with a humanized ambiguity message rather than picking a legacy fallback.
7. Result feedback must route active partial settlements to live war/settlement context. Sending `war_ended=False` outcomes to archived/recent-settlement ledger focus hides the remaining war from the player.
8. Incoming-offer `Accept` must preserve the offered package. Rebuilding a fresh generic `settlement_confirm` from live state while dropping offered clauses is not accepting an offer; it is restaging a different common-peace review.
9. Settlement command-fallback protection must be keyed by dialogue family/type, not by a drift-prone local action whitelist. A new settlement action id must not be able to fall through to synthesized natural-language command text.
10. Source-string tests are not enough. Every player-facing settlement action needs behavioral coverage, and Godot scripts need parse/load or executable coverage before manual smoke.
11. Failed settlement confirmation must not replace one false affordance with another. When acceptance, score, or hard stops block ratification, `confirm_settlement` is absent from `options[]`; the popup renders a settlement-blocked voice banner plus real routes such as edit/re-author when available or actionability-positive `Open War Detail` for live war reassessment. War Detail may expose Bilateral Peace or Armistice only through their own pair-scoped eligibility rules, and SC-10b must prove those tools exist before `Open War Detail` is treated as recovery. The rejected settlement popup itself must not emit direct substitute peace actions until SC-29 / G2-Slice-7 lands the pair-scoped contract. This is the canonical cleanup ratify decision: blocked ratification is explained by banner, body copy, and real recovery or terminal routes, not by a disabled `Ratify Settlement` button.

### Product Decision - Full Treaty Settlement

The product decision as of May 6, 2026 is **Full Treaty Settlement**, not permanent `Common White Peace`.

Required shape:

- Settlement entry opens a war-scoped draft package, not a bare empty-package confirmation.
- The player can add, remove, or change concrete treaty clauses before ratification.
- Every draft change re-runs common-peace preview: acceptance, hard stops, warnings, beneficiaries, ignored parties, remaining wars, political costs, and clause mutations.
- `Revise Terms` and incoming-offer `Request Revision` are real editor/counter routes, or absent until they are real.
- Incoming AI settlement offers preserve offer identity and exact offered clauses through accept/review/revision.
- `Ratify Settlement` is only available after the displayed acceptance verdict and hard-stop gate pass, and the backend enforces the same rule even if called directly.
- Settlement authoring uses the same conversational diplomacy standard as normal treaties: the player is choosing demands and offers through structured controls, Talleyrand explains why a court will or will not sign, and foreign-court copy answers in diplomatic voice rather than exposing scorer/debug state.

The existing one-to-one peace/proposal flow is the nearest UX and engineering analogue. Reuse its proven author -> preview -> adjust -> confirm pattern where possible, but keep common-peace state war-scoped (`war_id`, proposer side, accepting side/leader, covered enemies, selected target, route id, and draft terms).

Temporary hide/remove decisions are still valid when an implementation slice cannot complete the full route in one pass, but the hidden affordance and player impact must be recorded explicitly. Do not solve SC-1 by permanently rebranding the feature to white peace without a new product decision.

Two-way AI-to-player negotiation, AI counter-proposals, conference rounds, and ally veto systems are assigned to SC-30 / SC-32 and the landing slices in the Deferred Work Landing Ledger. This cleanup still must feel complete and usable: it delivers player-authored treaty terms with iterative acceptance preview, consequence preview, revise/re-author loops, and hard-stop refusal as the negotiation feedback loop. SC-5 defer-and-hide ensures no two-way negotiation controls are exposed until the AI counterpart exists end to end.

### Player-Facing Vocabulary

The player-facing term is **Settlement**. UI copy should use `Settlement`, `Open Settlement`, `Ratify Settlement`, `Settlement History`, and clause-specific treaty language inside the settlement flow. `common peace` remains an internal/backend command concept and save-compatible implementation term; it must not appear as the normal player-facing label for this flow. `treaty` may describe concrete authored clauses or stored records, but it must not be used interchangeably with the top-level CTA or route name.

Editor and review verbs are part of the same vocabulary contract:

- EDIT mode uses `Submit for Review` for the action that moves a valid draft into REVIEW. The bare label `Submit` is forbidden on player-facing settlement action rails because it reads like ratification or commitment.
- REVIEW mode uses `Ratify Settlement` only for the mutation-capable action after the fresh acceptance and hard-stop gate passes.
- Draft dismissal uses `Back Out` from the editor/review surface, then `Discard draft and back out` / `Keep draft and stay in editor` inside the discard-confirm surface when a non-empty draft exists.
- `Open Settlement History` means "open the Diplomatic Ledger to the Settlement History / `PEACE & SETTLEMENT HISTORY` focused row." If the implementation cannot make that landing visually match the label, the action must be renamed to `Open in Diplomatic Ledger` before it ships.

Required vocabulary tests: `test_editor_action_rail_uses_submit_for_review_label_not_bare_submit`, `test_discard_confirm_popup_options_are_two_actions_and_outer_cancel_is_keep_draft`, and `test_open_settlement_history_route_lands_in_settlement_history_section_with_matching_header`.

### Routing Boundary

Three peace paths exist, and the player must always know which one applies:

- **Settlement** covers multi-party wars with more than two total participants. It is the only path that can resolve some hostile pairs while leaving others active.
- **Bilateral Peace** covers one-to-one wars. It ends that war in one transaction.
- **Armistice** covers any war as a temporary cease-fire that does not transition the war to peace.

Settlement controls must not appear on one-to-one wars; SC-10 enforces this on war-detail and war-status rows. Bilateral peace controls must not appear as the default multi-party war settlement path unless the player explicitly drops into an approved single-pair scope.

When SC-10 hides Settlement controls on a one-to-one war row or detail surface, the same player surface must still expose the appropriate substitute peace affordance: `propose_peace` / Bilateral Peace and `propose_armistice` where eligible. Hiding Settlement without a reachable bilateral peace or armistice path on war detail and war status fails this spec, because it regresses the player from a visible but wrong CTA to no usable peace CTA.

Rejected multi-party settlement recovery is different: `Open War Detail` is a route back to live war context, not a promise that a bilateral peace or armistice action exists for the selected pair. War Detail renders pair-scoped Bilateral Peace / Armistice controls only if their own eligibility probes pass for the selected target; otherwise it renders humanized no-current-pair-alternative copy and leaves the player in the live war context. Direct rejected-popup CTAs such as `Seek Armistice Instead`, `Seek Bilateral Peace`, or settlement-family wrappers around those actions remain forbidden until SC-29 lands scope, handoff payload, eligibility helper, voice, and behavior tests.

Rejected-popup substitute peace timeline:

- Cleanup default before SC-29: `Seek Armistice Instead`, `Seek Bilateral Peace`, and any settlement-family wrapper around `propose_armistice` / `propose_peace` are absent from `settlement_confirm`, `recommended_alternatives[]`, mailbox rows, notifications, dispatch, and Godot branches.
- After SC-29 / G2-Slice-7 lands: those labels may appear only as pair-scoped actions with `scope="selected_pair"`, a selected target, a positive `evaluate_pair_peace_substitute_eligibility(...)` verdict, committed SC-19 voice copy, and SC-26 draft stale/invalidation behavior.
- After SC-29 when the selected pair is ineligible: the substitute labels are absent; War Detail or the popup renders no-current-pair-alternative copy or terminal close copy instead of a disabled or refusal-only substitute CTA.

### Disabled vs Hidden Affordance Policy

Settlement-family action buttons must distinguish temporary timing gates from missing capability. A disabled button is allowed only when the action exists, the payload can execute the named behavior, and the blocker can clear by deterministic time/resource refresh without changing the player's requested route. A disabled button must carry `disabled_reason_display`, a concrete unblock condition, and behavior coverage proving a later click can execute the same action.

State-gated, capability-gated, or future-system actions are absent rather than disabled. This includes rejected Ratify, Revise without an edit-capable route, request-terms without SC-30 lifecycle, direct pair-substitute CTAs before SC-29, dependency/surrender controls before SC-31, and any route whose target surface cannot perform the named action. Explanatory body copy or non-action status rows may name why an action is unavailable, but they must not be styled or wired as a clickable/disabled control.

Canonical helper mapping:

- `evaluate_pair_peace_substitute_eligibility(...)`: only `cooldown_active` may render a disabled pair-substitute button after SC-29. `already_at_peace`, `already_in_armistice`, `pair_not_at_war`, `war_archived`, `actor_not_at_war_with_target`, `target_not_selected_pair`, `target_not_in_war`, `settlement_collision_active`, `insufficient_resources`, and `malformed_route` hide the substitute action from `settlement_confirm` and render body/status copy or War Detail context instead.
- `evaluate_war_detail_actionability(...)`: `actionable=false` never renders `Open War Detail` as a recovery button. Refusal codes `war_archived`, `selected_pair_missing`, `pair_not_at_war`, `pair_already_resolved`, `editor_cannot_change_blocker`, `no_peace_seeking_control`, `settlement_collision_active`, `request_terms_ineligible`, and `malformed_route` produce history, edit, or terminal close routes according to the failure-state table.
- `evaluate_open_settlement_eligibility(...)`: normal row/detail surfaces may show explanatory non-action copy for `not_at_war`, `inactive_war_instance`, `not_side_leader`, `no_unresolved_hostile_pairs`, `no_coverable_enemy`, `settlement_dialogue_active`, and `war_state_changed_since_open`, but they must not render a disabled settlement action button unless the same surface also exposes a concrete existing alternative such as Bilateral Peace / Armistice where eligible.

Required tests: `test_pair_substitute_temporal_refusal_codes_render_disabled_with_reason`, `test_pair_substitute_terminal_refusal_codes_render_absent`, `test_war_detail_actionability_negative_hides_open_war_detail_recovery`, `test_open_settlement_terminal_eligibility_renders_non_action_copy_not_disabled_button`, and `test_disabled_vs_hidden_policy_maps_all_helper_refusal_codes`.

### Canonical Settlement Clause Schema

All settlement editor writers, backend preview validators, staging code, merge logic, presentation, and ratification readers use this exact wire schema. Aliases such as `target`, `imposer`, `payer`, or `recipient_nation` are forbidden unless this table is explicitly amended. Unknown or alias-only keys must fail POST preview with `disabled_reason_display` and an offending clause index.

| Clause type | Landing status | Required keys | Optional keys | Merge identity |
| --- | --- | --- | --- | --- |
| `peace` | Live in G2-Slice-1 | `type` | none | `(type)` |
| `territory_cede` | Live in G2-Slice-1 | `type`, `from`, `to`, `region` | none | `(type, from, to, region)` |
| `gold_indemnity` | Live in G2-Slice-1 | `type`, `from`, `to`, `amount` | none | `(type, from, to)` |
| `gold_per_turn` | Live after SC-33 / G2-Slice-9 | `type`, `from`, `to`, `amount`, `turns` | none | `(type, from, to)` |
| `forced_alliance` | Live in G2-Slice-1 as demand-only | `type`, `from`, `to` | `includes_continental_system` | `(type, from, to)` |
| `vassalage` | Live after SC-31 / G2-Slice-8 | `type`, `from`, `to` | none | `(type, from, to)` |
| `subjugation` | Live after SC-31 / G2-Slice-8 | `type`, `from`, `to` | none | `(type, from, to)` |
| `liberation` | Live after SC-31 / G2-Slice-8 | `type`, `vassal_nation`, `lord_nation`, `liberator` | none | `(type, vassal_nation, lord_nation, liberator)` |

Clause ordering within `settlement_terms[]` is presentation-only. Preview, acceptance scoring, and mutation must produce the same result regardless of clause order. The editor may reorder clauses for display grouping without changing outcome.

Covered scope is authored settlement data, not entry-route metadata. POST preview validates every material clause against the current `covered_enemy_participants`: any clause whose burdened or benefiting enemy is no longer covered, and is not a valid proposer-side beneficiary, returns `clause_target_uncovered` with the offending clause index and field. Changing the Covered Enemies picker therefore refreshes preview, invalidates referencing clauses until edited or re-covered, and never silently swaps a clause target to the accepting leader, first covered enemy, or coalition leader.

Canonical clause names are not a promise that every clause is live in G2-Slice-1. The `Landing status` column is normative for editor availability. First-slice live controls are `peace`, `territory_cede`, `gold_indemnity`, and demand-only `forced_alliance`; after SC-31, `vassalage`, `subjugation`, and `liberation` are also live; after SC-33, `gold_per_turn` is also live with `amount >= 10` and `1 <= turns <= 20` validator bounds. No canonical clause type remains hidden after SC-33. Hidden canonical clauses must be absent from `available_clause_types[]`, `clause_control_schema`, Add Clause controls, editor presets, concession baselines, mailbox/request-terms payloads, labels, and generated player copy; same-slice CI must fail if any hidden canonical clause label leaks before its owning landing row closes, including greyed-out or disabled labels. Required tests: `test_canonical_clause_schema_table_marks_landing_status_for_each_row`, `test_post_preview_available_clause_types_excludes_all_interim_hidden_clauses_until_landing`, `test_hidden_clause_types_do_not_leak_as_visible_or_disabled_labels`, and `tests/test_settlement_dependency_clauses.py::TestClauseControlSchema`.

### SC-1 Conflict Matrix

POST settlement preview must reject these named conflict classes with `disabled_reason_display` plus an offending clause index and field when applicable:

| Conflict code | Invalid shape | Player/implementation risk |
| --- | --- | --- |
| `duplicate_peace_clause` | More than one `{"type": "peace"}` clause | Lets a no-op clause masquerade as multiple authored concessions. |
| `duplicate_material_clause` | Two identical merge identities for `territory_cede`, `gold_indemnity`, `gold_per_turn`, `forced_alliance`, `vassalage`, `subjugation`, or `liberation` | Makes merge behavior order-dependent. |
| `region_double_ceded` | Same `region` ceded to two recipients or by two payers in one draft | Produces impossible mutation preview. |
| `gold_payment_budget_conflict` | Lump-sum plus recurring gold obligations from one payer exceed validator-approved payable capacity | Teaches the player an unaffordable settlement is valid. |
| `same_side_from_to` | Material clause uses `from` and `to` on the same settlement side unless a same-side beneficiary rule explicitly allows it | Turns treaty terms into internal transfers without player clarity. |
| `clause_target_uncovered` | Clause references a nation no longer in `covered_enemy_participants` or a valid same-side beneficiary set | Lets the Covered Enemies picker lie about scope. |
| `dependency_clause_conflict` | `vassalage`, `subjugation`, or `liberation` targets the same nation in incompatible ways | Creates contradictory dependency aftermath. |
| `protected_home_or_capital_cede` | `territory_cede` targets a capital/home region without an explicit hard-stop override | Silently violates territory safety rules. |

### Clause Display Vocabulary

The wire keys above are not player-facing labels. The editor, preview, dispatch, and ledger must use clause-specific vocabulary so `from` / `to` never leak as field labels.

| Clause type | Player-facing field labels | Direction badge / display prose |
| --- | --- | --- |
| `peace` | no fields | badge `Mutual`; display prose "End hostilities (no material change)" |
| `territory_cede` | `Ceding nation`, `Receiving nation`, `Region` | badge `Conceded` and prose "Offered to <them>" when the player/proposer side is ceding; badge `Demanded` and prose "Demanded from <them>" when the accepting side is ceding |
| `gold_indemnity` | `Payer`, `Recipient`, `Amount` | badge `Conceded` and prose "Offered to <them>" when the player/proposer side pays; badge `Demanded` and prose "Demanded from <them>" when the accepting side pays |
| `gold_per_turn` | `Payer`, `Recipient`, `Amount per turn`, `Turns` | same badge/prose rules as gold indemnity |
| `forced_alliance` | `Nation forced into alliance`, `Alliance imposed by`, `Continental System inclusion` | badge `Demanded`; prose "Imposed on <them>"; any future voluntary alignment offer needs its own product decision and cannot reuse forced-alliance copy |
| `vassalage` | `Nation becoming vassal`, `Lord nation` | badge `Demanded` or `Conceded` by beneficiary direction; prose "Submits to <lord>" |
| `subjugation` | `Nation being subjugated`, `Subjugating nation` | badge `Demanded` or `Conceded` by beneficiary direction; prose "Forced under <lord>" |
| `liberation` | `Vassal to liberate`, `Current lord`, `Liberator` | badge `Demanded` or `Conceded` by beneficiary direction; prose "Liberate <vassal>" |

`direction_tag` is the compact badge value and must be one of `Demanded`, `Conceded`, or `Mutual`. `direction_display` is the human sentence shown in preview/review copy. Tests must fail if the two disagree, such as `direction_tag="Conceded"` with display prose that says "Demanded from <them>". Behavior tests must also fail if editor controls, preview rows, or generated settlement copy show literal `from` / `to` labels to the player, or if structured-control labels use internal enum phrasing instead of this table.

### Concession And Treaty Conversation Contract

Losing-side peace is owned by SC-1's first editor floor, not by a future unowned "ask for terms" feature. Concessionary authoring requires no new clause types. The existing clause schema supports concessions when authored direction benefits the accepting side: France can be the `from` / payer / ceding nation, and the enemy can be the recipient. The editor presents this as an offer-mode conversation, not as a new clause type, incoming-offer wait, mailbox action, or free-text command.

Required behavior:

- The editor exposes a clear demand/offer direction for every live material clause. `territory_cede` and `gold_indemnity` must support player-as-ceder and player-as-payer packages in G2-Slice-1.
- The player can request a Talleyrand concession baseline while losing. This is a draft-suggestion affordance using existing MVP clauses (`peace`, `territory_cede`, `gold_indemnity`), not an incoming AI offer, not a mailbox route, and not a free-text command.
- `losing_for_concession_baseline` is a runtime predicate owned by the settlement preview validator: the proposer side is losing when `side_pressure_score <= -20` for the current `war_id` and covered scope. The preview reads `side_pressure_score` from the existing `calculate_common_peace_acceptance(...)` pipeline rather than recomputing it. Entry surfaces may precompute it for visibility, but POST preview remains the source of truth. This predicate is not the same as "all clauses reject"; a winning player with an over-harsh draft can receive blocked-ratification guidance without seeing the losing-side concession baseline control.
- Both `build_settlement_preview(...)` (POST `/diplomatic_preview?mode=settlement`) and `build_settlement_confirm_dialogue(...)` (the staged `settlement_confirm` payload) emit the same three keys at the canonical positions: `losing_for_concession_baseline: bool` (predicate result), `concession_baseline_visible: bool` (predicate AND material-baseline-can-be-generated), and `concession_baseline: {"terms": List[Clause], "reasoning": str}` (the deterministic baseline draft and a humanized rationale). When `concession_baseline_visible=false`, `concession_baseline` is `null` or absent and Godot must not synthesize a stub baseline.
- Acceptance scoring evaluates each term from the accepting side's perspective. Clauses that benefit the accepting side reduce effective harshness or add a named `concession_credit` component; clauses that burden the accepting side increase harshness. Direction must be visible in the component explanation.
- The concession baseline uses only complete canonical clauses and must be deterministic in normal gameplay and in fixtures. It starts by evaluating a neutral `{"type": "peace"}` floor, but the concession-baseline action is available only when the algorithm can add at least one material concession beyond that neutral floor. It then proposes one `gold_indemnity` from the player/proposer leader to the accepting leader for the smallest positive amount among: available treasury above a 500-gold reserve, 1500 gold, and `max(300, acceptance_gap * 100)` where `acceptance_gap` is `max(0, threshold - peace_only_score)` and `peace_only_score` is the `score` returned by `calculate_common_peace_acceptance(...)` against `settlement_terms=[{"type": "peace"}]` for the same `war_id`, proposer side, and `covered_enemy_participants`. The treasury-reserve candidate is `payer_balance - 500`; non-positive candidates drop out of the `min(...)` set, so the algorithm only ever selects a strictly positive payable amount. If the positive-candidate set is empty, it skips gold and explains why. The baseline favors affordability over guaranteed acceptance: if gold alone does not reach `near_acceptable`, the algorithm escalates to territory rather than silently scaling the indemnity beyond the conservative cap. Region selection is deterministic: legal transferable, non-capital, non-home regions controlled by the proposer side are sorted by shortest map distance to the accepting leader's home/capital when map adjacency data exists, then by lowest economic value, then by region name. Map distance uses BFS over `region.adjacent_regions` from `NATION_CAPITALS[accepting_leader]` with a bounded search depth; regions unreachable inside the bound fall through to the lower priority sort keys rather than being excluded. If no positive payable gold and no legal transferable region exist, the concession-baseline action is hidden or replaced by non-action guidance copy; it must not expose `Generate concession baseline`, `Re-author with concessions`, or any other concession-labeled action that produces only peace.
- When `losing_for_concession_baseline=true` and the baseline can produce a material concession, `Generate concession baseline (Talleyrand)` is primary-weighted and visible in the first EDIT frame without scrolling, above or adjacent to the Add Clause picker in the Clause controls band and mirrored in the Action rail. Required test: `test_concession_baseline_button_is_visible_at_first_paint_when_actor_is_losing_side`.
- Both `Generate concession baseline (Talleyrand)` in EDIT and `re_author_with_concessions` in REVIEW revalidate `losing_for_concession_baseline` and material-baseline availability through POST preview at click time. If visibility was computed from stale state and the predicate flips from true to false, the click leaves the current draft unchanged, renders humanized "no longer eligible" copy, and does not apply a baseline, consume resources, or consume a stale-reopen attempt. If the predicate flips from false to true, no hidden click target appears retroactively; the player sees the baseline only after the next preview/entry render.
- If the deterministic baseline still leaves the package below `near_acceptable`, the preview must show the remaining top blocker and at least one concrete next authoring step when one exists, such as increasing payable gold, adding a different transferable region, or removing an impossible demand. It must not render as a terminal "still rejected" dead end after the player used the suggested baseline. Required test: `test_concession_baseline_still_rejected_names_next_authoring_step_or_terminal_reason`.
- The `settlement_losing` / `settlement_rejected` smoke fixture must publish a transferable non-capital `concession_region`, France must have at least 1500 gold or an explicitly documented lower fixture amount, and the fixture's Talleyrand baseline must be derived from the normal algorithm above. Any lower amount or missing region is a fixture failure, not a reason to silently weaken the concession test.
- Peace-only losing drafts are valid previews but must not pretend to be concessionary. If a losing-side `{"type": "peace"}`-only draft stays below threshold, the preview panel shows humanized guidance such as "This package offers no material change. Authoring concessions may improve acceptance." This is copy guidance only, not an AI-offer wait or separate action.
- Invalid concession attempts fail POST preview with humanized `disabled_reason_display`; they must not silently flip direction, strip the clause, or render a court response as if a valid offer exists.
- The review voice mirrors standard treaty conversations: Talleyrand names the strongest blocker or concession, foreign-court lines answer the package in their register, and no raw `from` / `to`, `verdict`, or component ids appear in player copy.

Required tests: `test_losing_side_authored_concession_draft_can_reach_accept_band_with_realistic_war_state`, `test_concession_terms_move_acceptance_in_accepting_side_direction`, `test_talleyrand_concession_baseline_uses_existing_clause_schema`, `test_losing_peace_only_preview_prompts_concession_without_offer_wait`, `test_concession_review_uses_treaty_conversation_voice_not_debug_terms`, `test_concession_baseline_real_gameplay_chooses_payable_amount_and_transferable_region_outside_fixture`, `test_concession_baseline_button_is_visible_at_first_paint_when_actor_is_losing_side`, `test_concession_baseline_still_rejected_names_next_authoring_step_or_terminal_reason`, and `test_concession_baseline_action_hidden_when_only_peace_clause_can_be_generated`.

### Spec Review Gate

Any dedicated settlement/peace UX spec review before implementation, smoke, or branch-target reconciliation uses the established scoring categories: Fun, Clarity, Work Segmentation, Contradiction-Freedom, and Completeness. Each category must score at least 8/10. Any unresolved P0 or P1 finding makes the verdict NO-GO regardless of scores. The review must name the reviewer, date, target branch/commit, current cleanup spec version, and review-session reference.

Recognized verdicts are:

- `GO`: the spec and the implementation/readiness evidence both pass; the named next implementation or smoke slice may start.
- `GO-pending-verification`: the spec contract is binding and scores pass, but a named verification gate such as G2-Slice-0 / pre-smoke branch verification must close before any implementation slice may start.
- `NO-GO`: at least one score is below threshold or an unresolved P0/P1 spec finding remains; the minimum spec edits must be listed.

The verdict must be recorded in `docs/STATUS.md` using the exact same verdict token. A `GO` or `GO-pending-verification` entry must name the exact spec version and review-session reference; a `NO-GO` entry must name the minimum spec edits blocking Gate 1. ### White Peace Affordance

Empty-package ratification is forbidden through the settlement editor. The wizard's `Open Settlement` flow lands in EDIT with `Ratify Settlement` gated on `len(settlement_terms) > 0`; clicking Ratify with no authored clauses is unreachable. The "no clauses authored yet" baseline message remains visible until the player authors at least one clause or backs out.

White peace as a distinct player intent is reachable through a separate, labeled `Propose White Peace` action surfaced by the F1 diplomacy wizard alongside `Open Settlement`. The action opens a dedicated white-peace confirmation popup that:

- Names the war and covered enemy participants explicitly.
- States in player copy that no terms will be exchanged.
- Runs the same acceptance scorer against an empty draft; if acceptance rejects, the popup hard-stops with the standard blocked-ratification banner and does not offer Ratify.
- On accept, ratifies through `ratify_settlement_confirm(...)` with `settlement_terms=[]` and emits a `settlement_summary` event tagged `white_peace=true` so dispatch / ledger / campaign log render the outcome as a labeled white peace rather than a generic settlement.

Backend action id: `propose_white_peace` is a new entry in `VALID_ACTIONS` distinct from `propose_common_peace`. The F1 wizard CTA, the structured diplomatic-action endpoint, and result-feedback / ledger / dispatch surfaces all key on `propose_white_peace`. `propose_common_peace` continues to own the editor / settlement-review path with authored `settlement_terms`; the two action ids do not share an executor entrypoint, and Godot routes only `propose_white_peace` to the labeled white-peace path.

Popup architecture: the white-peace popup reuses the existing `settlement_confirm` dialogue type with a `white_peace: bool = true` flag on the staged dialogue. The flag inherits the existing `proposal_confirm_popup.gd::_build_settlement_content` surface, voice families, dialogue-manager lifecycle, and ratification handler; it changes only the header / banner label variant, the empty-Ratify gate exemption, and the propagated `white_peace=true` field on the emitted `settlement_summary` event. No new Godot popup file is required.

Empty-Ratify editor gate: when a `settlement_confirm` dialogue is staged with `caller_kind="player_editor"`, `settlement_terms == []`, and `white_peace=false`, `confirm_settlement` is absent from `options[]` and `available_action_ids[]` regardless of acceptance verdict. This is a backend defense-in-depth gate on top of the editor's `Submit for Review` disabling rule; the player surface should never reach this dialogue with an empty draft, but the backend still refuses to mint Ratify for it. White-peace dialogues set the flag explicitly to bypass the gate.

`G2-Slice-W1` (see the slice budget table below) is the cleanup slice that lands the wizard CTA, the new action id, the dialogue flag, the ratification propagation, and the empty-Ratify gate together. Subsequent slices may not split this contract across multiple commits.

The typed-command path `propose common peace with X` is treated as a debug/parser-only entry: it remains in `VALID_ACTIONS` and may stage `settlement_confirm` with an empty draft, but no player surface routes through it. Player smoke evidence covers the wizard CTAs, not the typed command.

### Rejected Settlement / Losing-Side UX Contract

The common settlement confirmation popup is a ratification checkpoint. It reviews a concrete settlement package and asks whether the accepting side will take it. It is not, by itself, a treaty editor, a surrender menu, or an incoming-offer mailbox. When acceptance fails, the UI must explain that the proposed package cannot be ratified in its current form and then route the player toward the real peace tools that exist.

Required interim behavior before full treaty authoring:

- Omit `confirm_settlement` from `options[]` and `available_action_ids[]` when verdict is reject/blocked, score is below `acceptance.threshold`, or hard stops exist. The renderer must not assume Ratify is present.
- Render `settlement_blocked_for_ratification_talleyrand` or the equivalent Voice Bible 16.1 blocked-ratification family as the primary banner, with exact blocker copy in the popup body.
- Do not render `Ratify Settlement` as a disabled placeholder. Blocked-ratification reason belongs in the banner/body and recovery routes. A disabled Ratify button is a false affordance because it reads like a future click target inside the same popup.
- Do not show a working `Revise Terms` action unless it opens an edit-capable draft route that preserves `war_id`, covered participants, selected target, and current `settlement_terms`.
- If revision is not yet implemented, hide `Revise Terms` entirely and record the temporary hide with owning SC row, restoring slice, STATUS line, and CI gate. Disabled placeholder buttons are forbidden because they read like a player action. Do not route it to a no-op reopen loop.
- If the war is active, include `Open War Detail` as a structured recovery route back to the exact live war context only when SC-10b evidence exists and the War Detail actionability probe below is positive. War Detail may show Bilateral Peace or Armistice only when the selected pair is eligible under those systems' own probes; otherwise it must show humanized no-current-pair-alternative copy. Do not surface a direct armistice or bilateral-peace action from `settlement_confirm` until SC-29 / G2-Slice-7 lands the pair-scoped contract; settlement is war-scoped and armistice / bilateral peace are separate pair-scoped flows.
- Minimum blocked-review recovery is part of G2-Slice-1, not later polish: any blocked REVIEW created by below-threshold submit, hard stop, stale state, or rescore failure must expose at least one real edit/re-author, history, or terminal close route in the same implementation slice. `Open War Detail` counts as a recovery route only after SC-10b executable evidence proves War Detail renders pair-scoped Bilateral Peace / Armistice controls or a concrete no-current-pair explanation for the selected target.
- If the war has archived, include `Open Settlement History` when a route id exists. Only malformed payloads with no recoverable active or archived target may collapse to `Back Out` alone, and they must show humanized recovery copy.
- If AI settlement offers are deferred, do not imply that waiting will produce one. Enemy-offer waiting must not appear as an action, disabled action, label, route, or recovery hint while SC-5 is deferred.

War Detail recovery contract:

- The recovery action id is `open_war_detail`, with `recovery_route={"surface": "war_detail", "war_id": str, "selected_target_nation": str | null, "covered_enemy_participants": List[str], "source_route_id": str | null, "reason": str}`. Archived recovery uses `{"surface": "settlement_history", "route_id": str}`.
- `open_war_detail` dispatches through `main.gd` to `war_detail_popup.gd` on its existing CanvasLayer 30, dismisses/backgrounds the rejected settlement popup, and preselects `selected_target_nation` when the pair still exists. If the war archives between render and click, the handler follows the SC-14e click-time fallback: show humanized "this war is no longer active" copy plus `open_settlement_history` when a route id exists, otherwise terminal close copy.
- The settlement popup never emits `propose_armistice`, `propose_peace`, or a settlement-family wrapper for those actions. War Detail owns those structured controls and their normal costs, cooldowns, target pickers, and disabled reasons.
- `Open War Detail` cannot be advertised as a blocked-review recovery route until SC-10b proves War Detail renders pair-scoped Bilateral Peace / Armistice controls or a true no-current-pair terminal explanation for the selected target. Until SC-10b ships, blocked reviews with no edit or history route must use terminal close copy rather than routing the player into a second dead end.
- `Open War Detail` is not the primary answer for an editable rejected multi-party settlement. When the editor and concession baseline are available, `Re-author with concessions` / `Revise Terms` must appear before `Open War Detail`; otherwise the recovery path becomes reject -> War Detail -> Open Settlement -> reject, which is the same false-affordance class as the original Revise Terms bug.
- Choosing `Open War Detail` is a background-and-preserve transition, not ordinary Back Out. It preserves a non-empty unratified draft in `pending_settlement_drafts[draft_key]` without showing discard-confirm, because the player is following the spec-provided recovery route rather than abandoning the draft. This transition does not consume a SC-14b settlement reopen attempt; the substitute live-war surface is a different action family.
- If the player completes bilateral peace or armistice from War Detail, any preserved settlement draft whose `draft_key` covers the affected pair becomes stale. Reopening Settlement must run fresh POST preview before any ratification path appears; if the war state no longer supports the draft, the player sees a stale-draft notice and may discard or re-author.
- If the player cancels or fails the bilateral peace / armistice flow, returning to Settlement restores the draft as previous/stale and requires preview refresh before `Submit for Review` or Ratify.
- Normal Settlement entry from War Detail, wizard disambiguation, coalition detail, notification, dispatch, or ledger for the same `war_id`, selected target, and covered scope consumes a preserved same-turn scoped draft and opens EDIT with a visible "Draft restored from prior recovery" notice. There is no separate hidden Resume Draft affordance in cleanup. If more than one scoped draft matches a broad entry path, the entry shows a chooser rather than silently selecting one.
- One-to-one wars should not normally reach `settlement_confirm`; if a stale save or debug path does, `Open War Detail` is available only when War Detail can show eligible Bilateral Peace / Armistice controls or a concrete unblock condition such as cooldown turn, ineligible reason, or no-current-pair terminal copy. If both substitutes are ineligible and no unblock condition can be named, the settlement popup uses `settlement_no_alternative_route_chancery` terminal copy instead of routing the player into a dead end.
Required behavior tests: `test_failed_settlement_open_war_detail_preserves_draft_without_pair_action`, `test_open_war_detail_recovery_preserves_non_empty_draft_without_discard_prompt`, `test_open_war_detail_recovery_does_not_promise_ineligible_pair_action`, `test_open_war_detail_recovery_renders_pair_scoped_substitutes_or_terminal_close_not_humanized_dead_end`, `test_open_war_detail_handles_mid_click_archival_gracefully`, `test_bilateral_armistice_success_invalidates_only_matching_scoped_settlement_draft_with_notice`, `test_seek_armistice_instead_cta_absent_until_sc29_lands`, `test_one_to_one_stale_settlement_routes_to_war_detail_bilateral_tools`, `test_one_to_one_stale_settlement_with_no_eligible_substitute_shows_unblock_reason_not_silent_dead_end`, `test_settlement_entry_after_open_war_detail_recovery_restores_or_resumes_scoped_draft_per_spec`, and `test_settlement_entry_after_recovery_renders_draft_restored_notice_once_per_re_entry`.

War Detail actionability helper schema:

- `evaluate_war_detail_actionability(world, *, war_id, actor_nation, selected_target_nation, blocked_reason, settlement_terms, covered_enemy_participants) -> {"actionable": bool, "actionable_kind": str | null, "refusal_code": str | null, "disabled_reason_display": str | null, "recovery_route": Dict | null, "selected_pair": {"actor": str, "target": str, "war_id": str} | null}`.
- `actionable_kind` is a closed enum: `pair_peace`, `pair_armistice`, `settlement_editor_can_change_outcome`, `request_terms`, or `treaty_authoring`. Pure economy, recruit, repair, inspect, or generic ledger controls do not satisfy settlement recovery actionability.
- `request_terms` is valid only after SC-30 / Slice G1 ships the request-terms lifecycle, producer/cooldown state, UI, voice, and behavior tests. Before SC-30, `request_terms` maps to `request_terms_ineligible` and cannot make War Detail actionability-positive. `treaty_authoring` is positive only when the current editor route can actually change the blocker; it is not a generic "open the settlement feature" bucket.
- `settlement_editor_can_change_outcome` is positive only when the editor can change the current blocker, such as below-threshold acceptance, missing peace/material concession, or fixable clause validation. Reopening the same editor with an unchanged rejected package is not actionability.
- Closed `refusal_code` values are `war_archived`, `selected_pair_missing`, `pair_not_at_war`, `pair_already_resolved`, `editor_cannot_change_blocker`, `no_peace_seeking_control`, `settlement_collision_active`, `request_terms_ineligible`, and `malformed_route`.
- Required tests: `test_actionability_case_b_only_true_when_editor_can_change_outcome_not_just_open`, `test_actionability_case_d_excludes_unrelated_economy_recruit_repair_controls`, and `test_war_detail_actionability_helper_schema_matches_canonical_keys`.

- Required tests: `test_pair_substitute_eligibility_helper_schema_matches_canonical_keys` and `test_pair_substitute_refusal_code_taxonomy_is_closed_set`.

Draft identity contract:

- `draft_key` is `settlement_draft:{war_id}:{selected_target_key}:{covered_scope_hash}`. `selected_target_key` is the selected target nation or the literal `_none`. `covered_scope_hash` is the first 16 hex chars of SHA-256 over the ASCII JSON array of sorted unique `covered_enemy_participants` using compact separators `(",", ":")` exactly: no spaces, ASCII comma and colon, JSON string escaping, and deterministic sorted order. Example pre-hash bytes for Austria/Britain/Prussia are `["Austria","Britain","Prussia"]`; the test suite pins the resulting first-16-hex golden value for both backend and Godot. Do not use Python/Godot built-in hash functions, locale-dependent joins, unsorted input order, duplicate-sensitive scope strings, or serializer defaults that insert whitespace.
- Same-war same-scope restaging may merge compatible terms through SC-26. Cleanup default for same-war different-scope restaging is rejection-only: it returns `same_war_scope_collision` with the existing draft unchanged, `error_display` explaining that another scoped settlement draft is already active, and a recovery instruction to reopen or resolve the first draft before starting the second scope. A future chooser/replace-confirm path belongs to SC-32 unless this spec is amended with its payload, voice, and tests.
- `pending_settlement_drafts` serializes as a dict keyed by `draft_key`. Each record stores `war_id`, `selected_target_nation`, sorted `covered_enemy_participants`, `settlement_terms`, `created_turn`, `updated_turn`, `last_preview_hash`, and `clause_schema_version`.
- Loading an old draft after SC-31 / SC-33 or any later clause-type landing revalidates the saved terms against the current POST preview validator and the saved `clause_schema_version`. New clause types do not auto-appear in old drafts, hidden clause types do not become ratifiable by old saves, and invalidated drafts surface humanized re-author/discard copy instead of silently mutating.
- Required behavior tests: `test_same_war_different_selected_target_drafts_do_not_merge_or_clobber`, `test_scoped_settlement_draft_key_round_trips_save_load`, `test_scoped_draft_key_is_stable_across_order_duplicates_save_load_and_client_roundtrip`, `test_scoped_draft_key_backend_and_godot_match_golden_hash_for_compact_json_scope`, and `test_same_war_same_scope_merge_uses_sc26_clause_identity`.

Draft-discard notice contract:

- End-turn discard writes a one-shot `pending_settlement_draft_notices[]` entry or an explicitly equivalent dispatch/campaign-log notice with `war_id`, `turn_discarded`, `draft_clause_count`, `selected_target_nation`, and `message_display`.
- The notice survives save/load until rendered once, then clears. It must not restore the discarded draft or allow ratification from stale data.
- End-turn draft discard runs before the enemy-phase autosave records post-turn state. A manual save/load before end turn restores the draft; an autosave/load after end-turn discard restores only the one-shot notice, not the draft.
- Required behavior tests: `test_load_after_end_turn_does_not_silently_drop_draft_without_player_signal` and `test_enemy_phase_autosave_after_draft_discard_contains_notice_not_ratifiable_draft`.

Discard Draft Confirm Contract:

- Triggered by Back Out, Escape/window close/outside click, end-turn discard prompt, or any replace/overwrite flow when the current EDIT draft has at least one authored clause.
- Payload type is `settlement_discard_confirm` and uses `options[]` exactly as `[{ "action": "discard_draft_and_back_out", "label": "Discard draft and back out" }, { "action": "keep_draft_and_stay", "label": "Keep draft and stay in editor" }]`.
- `discard_draft_and_back_out` clears only the scoped `draft_key` and closes or returns to the caller specified by the invoking action. `keep_draft_and_stay` restores the same EDIT popup with the draft, covered scope, selected target, last preview, and focused clause intact.
- Outer cancel on the discard-confirm popup itself, including Escape/window close/outside click, is treated as `keep_draft_and_stay`; it never discards by implication.
- Voice family: `settlement_discard_confirm_talleyrand`. Resource cost follows SC-4b and is always zero.
- Required behavior test: `test_discard_confirm_popup_options_are_two_actions_and_outer_cancel_is_keep_draft`.

Required final behavior for losing-side peace:

- The player must be able to seek peace while losing. Settlement agency cannot depend on first becoming the winning side.
- Losing-side treaty packages must support concessionary terms through the same war-scoped authoring/preview/ratification pipeline. Cleanup-scope losing peace means player-authored concessions using canonical clauses, especially player-as-payer / player-as-ceder `gold_indemnity` and `territory_cede`, plus the neutral `peace` floor. `Ask for terms` belongs to SC-30's AI offer/request-terms landing slice; `Surrender terms` belongs to SC-31's dependency/surrender landing slice. Neither label may appear as a cleanup payload action, mailbox wait, backend command text, or editor preset before its landing slice ships.
- "Concession" is primarily an authoring and presentation direction, not a new required clause type. The canonical schema already supports concessions when a clause uses `from=France` / `to=<enemy>` or otherwise benefits the accepting side. The editor must surface per-clause `direction_display` such as "Demanded from <them>" versus "Offered to <them>" and acceptance scoring must treat the sign consistently through `concession_credit` / reduced harshness components.
- The first editor slice must include a discoverable concession baseline or suggestion affordance for losing players, such as `Generate concession baseline` or a Talleyrand suggestion using existing MVP clauses (`territory_cede`, `gold_indemnity`, `peace`). Without that, losing-side peace is technically possible but practically invisible.
- G2-Slice-1 includes peace-with-concessions in the live floor: the `territory_cede` and `gold_indemnity` controls must support player-as-ceder and player-as-payer packages, and those packages must run through the same preview, acceptance, and ratification gates as winner-favored demands.
- Acceptance scoring may make harsh player-favored terms impossible while losing, but it must not strand the player without any peace-seeking route.
- Incoming AI offers/counter-offers may complement losing-side peace only if SC-5 is explicitly reversed; they cannot be the only way for a losing player to pursue peace.
Required behavior test: `test_losing_side_authored_concession_draft_can_reach_accept_band_with_realistic_war_state`, using a losing France fixture with player-authored gold/territory concessions to Britain and asserting the preview reaches `accept` or `near_acceptable`. Absence tests: `test_ask_for_terms_absent_while_incoming_offers_deferred` and `test_surrender_terms_absent_until_dependency_clause_restoration`.

Rejected-popup presentation co-landings:

- `proposal_confirm_popup.gd::_build_settlement_content` must not render the outgoing "Will <leader> accept this settlement?" header when `can_ratify=false`. Blocked/rejected reviews render the Voice Bible 16.1 blocked-ratification banner followed by `ratify_blocked_reason`.
- Blocked hard-stop acceptance suppresses numeric `0 / 50 - Reject/Blocked` copy. Backend acceptance display should use null/absent `total` and `threshold` for hard-stop blocked states, and Godot must render blocker copy instead of coercing null to `0`.
- Production Godot must not show developer text such as `Settlement payload incomplete: missing ...`. Malformed settlement payloads render humanized recovery copy: "Settlement details could not be loaded; reopen from War Status."
- Incoming and outgoing settlement voices are split, or incoming settlement offers remain hidden under SC-5.
- Production surfaces must not show backlog-copy labels such as "Term editor not available yet", "Wait for Enemy Offer", "Seek Armistice Instead", "Ask for terms", or "Surrender terms" unless the owning landing row for that exact action is implemented end to end with tests.

### Full Treaty Settlement Flow

The normal player path is: (1) wizard, war detail, or coalition detail emits `settlement_clicked(war_id, selected_target_nation, covered_enemy_participants)`; (2) Godot opens the editor on the existing `proposal_confirm_popup.gd` settlement surface in `EDIT` mode with `settlement_terms=[]`, no saved draft record yet, a "no clauses authored yet" baseline panel, and no previous-band/delta copy until the first completed POST-previewed clause commit; (3) the Covered Enemies editor band lets the player change `covered_enemy_participants` before `Submit for Review`, with at least one covered enemy required; (4) clause-add, clause-remove, clause-edit, and covered-scope commits trigger `POST /diplomatic_preview?mode=settlement` with the current `settlement_terms` and `covered_enemy_participants` and refresh acceptance, warnings, hard stops, `remaining_wars[]`, `ignored_participants[]`, and `disabled_reason_display`; (5) `Submit for Review` sends `/command` with `action=propose_common_peace`, `war_id`, `selected_target_nation`, `covered_enemy_participants`, `settlement_terms`, `draft_key`, and player-editor caller context after one final POST preview and any required below-threshold warning confirmation; (6) `_execute_propose_common_peace` revalidates the submitted terms and covered-enemy scope against the SC-1 POST preview taxonomy, then forwards `settlement_terms`, `covered_enemy_participants`, `selected_target_nation`, and `caller_kind="player_editor"` into `stage_settlement_confirm(...)`; (7) `settlement_confirm` transitions the same popup to `REVIEW` mode and reviews the same package and scope; (8) `Revise Terms` returns the same package and covered-enemy scope to `EDIT` mode only when an edit-capable route exists; (9) only review-mode `Ratify Settlement` can mutate, and it re-runs `calculate_common_peace_acceptance(...)` fresh before mutation. Editor-mode ratification shortcuts are forbidden in this cleanup phase; editor mode submits for review, and review mode owns ratification.

Entry-scope producer rules:

- Wizard entry seeds `selected_target_nation` from the chosen nation and seeds `covered_enemy_participants` with that nation plus same-side enemy participants in the matched `war_id` that are hostile to the proposer side. If more than one shared war matches and no `war_id` is supplied, the wizard rejects ambiguity rather than choosing a sorted first war.
- War-detail entry uses the clicked row's enemy as `selected_target_nation` and the same covered-scope rule as wizard entry.
- Coalition-detail focused-row entry uses the focused enemy as `selected_target_nation`; without a focused row, whole-war entry seeds all enemy participants in the shared war and must show the Covered Enemies band before preview. A coalition leader is not a valid silent replacement for the focused enemy.
- Coalition detail caps visible settlement per-war buttons at `COALITION_SETTLEMENT_VISIBLE_PER_WAR_BUTTONS = 4`: the focused/primary eligible war plus up to three secondary eligible wars, followed by a `+N more wars` expander that reveals the remaining eligible per-war buttons without overflowing the 1080p panel. Hidden overflow rows are not disabled or lost; they become actionable after expansion.
- Notification, dispatch, ledger, result-feedback, and stale/revise reopen paths restore `covered_enemy_participants` and `selected_target_nation` from the staged dialogue or persisted event. They do not recompute scope from first covered enemy except as diagnostic fallback.
- Typed/free-text command entry defaults to all enemy participants for the matched `war_id`; when multiple shared wars match and no `war_id` is supplied, it rejects with a humanized ambiguity message.
- Player-facing typed/free-text settlement entry follows the same authoring contract as wizard/detail entry. It must not stage a REVIEW with `can_edit_terms=false` from player-authored terms; it either opens EDIT with the parsed/empty draft under `caller_kind="player_editor"` or rejects with humanized copy. Direct REVIEW staging with `caller_kind="debug"` / `system` is allowed only for test/debug fixtures and must not become the normal player route.

`selected_target_nation` is the canonical player-selected court/focus field. Any legacy `target_nation` field in settlement payloads must equal `selected_target_nation`; if both are present and differ, preview/submit fails closed with `target_selected_target_mismatch`, humanized copy, and no staged dialogue.

Canonical payload schemas:

- POST settlement preview request: `{"mode": "settlement", "war_id": str, "actor_nation": str, "selected_target_nation": str, "covered_enemy_participants": List[str], "settlement_terms": List[Clause], "caller_kind": "player_editor", "draft_key": str | null}`.

Alias keys such as `accept_threshold` may exist inside the scorer only; presentation and ratification consumers read `threshold`.

A legacy `target_nation` alias may be accepted only when it exactly equals `selected_target_nation`; otherwise the executor returns `target_selected_target_mismatch`. The executor reruns POST-preview validation before staging and returns `submitted_terms_failed_revalidation` without staging on mismatch.
- `settlement_confirm` REVIEW payload: top-level `type="settlement_confirm"`, `dialogue_mode="REVIEW"`, `war_id`, `route_id`, `draft_key`, `selected_target_nation`, `covered_enemy_participants`, `settlement_terms`, `acceptance`, `hard_stops`, `can_ratify`, `can_edit_terms`, `available_clause_types[]` when editable, `options[]`, `available_action_ids[]`, `editor_route` when editable, and `recovery_route` when blocked/stale.

`caller_kind` legal values are `player_editor`, `legacy_typed_command`, `ai_system`, `debug_system`, and future `ai_war_leader_offer` after SC-30 reversal. `can_edit_terms` is true if and only if `caller_kind == "player_editor"`, the staged dialogue still resolves to an active `war_instance`, `settlement_terms` is non-empty, and the latest POST preview exposes non-empty `available_clause_types[]`. POST preview is triggered by a clause completion event: all required fields for that clause are present and the last edited field commits via blur, Enter, picker selection, or an explicit Confirm Clause control. Subsequent edits to a complete clause re-trigger preview on the next completion event, debounced by 250 ms in Godot. Preview refresh manually replays the latest complete draft and covered scope without changing clause data. Required test: `test_post_preview_triggered_on_clause_completion_event_not_every_keystroke`.

A component is included when its signed contribution changes by at least 5 points, its display band changes, or it becomes the top blocker; otherwise it may be omitted to keep the payload readable. Required test: `test_acceptance_changed_after_staging_delta_payload_names_material_component_changes`.

Dialogue hard-stop classification:

- `EDIT` mode is not a hard stop. The player may end the turn from an editor draft; end turn discards unsubmitted drafts through the SC-2 discard-notice contract.
- `REVIEW` and `BLOCKED_TERMINAL` modes are hard stops. They require ratification, edit/recovery/history, or Back Out/Close before normal commands continue.
- EDIT <-> REVIEW cycles caused by normal player revision are not SC-14b stale-reopen attempts and have no loop cap. SC-14b counts only backend `must_reopen` stale/changed-state recovery attempts.

### Editor Layout Contract

The settlement editor is not just a route to POST preview. It uses this panel map inside the existing settlement popup surface:

| Vertical band | EDIT mode | REVIEW mode |
| --- | --- | --- |
| Header | Settlement title, war label, selected target, voice line, visually prominent mode badge `Editing draft` | Settlement title, war label, selected target, voice line, visually prominent mode badge `Reviewing draft` |
| Covered enemies | Editable checklist of hostile enemy participants in the selected `war_id`, seeded by entry-scope rules; at least one enemy must stay selected | Read-only covered-enemy chips plus ignored/still-at-war participants |
| Clause package | Left column clause list with validation state, remove/reorder affordances, and selected-clause focus | Read-only clause summary with applied-clause preview links |
| Clause controls | Right column structured Add Clause controls, inline editor for the selected clause, merge-conflict resolution sub-controls when active, and a first-frame visible primary `Generate concession baseline (Talleyrand)` trigger above/adjacent to Add Clause when `losing_for_concession_baseline=true` and a material baseline exists | Hidden; replaced by beneficiaries / ignored parties / remaining-war summary |
| Preview panel | Acceptance, hard stops, warnings, beneficiaries, ignored parties, political cost, mutation preview, below-threshold submit warning, merge-conflict banner with `Discard new clause` / `Replace active clause`, stale/previous marker | Same preview panel, locked to the staged package unless Revise Terms returns to EDIT |
| Action rail | Back Out, Preview refresh, `Generate concession baseline (Talleyrand)` when `losing_for_concession_baseline=true`, `Submit for Review` | Back Out, Revise Terms only when edit-capable, Ratify Settlement only when active per SC-3/SC-4, recovery route when ratification is blocked |

- Add Clause controls: structured controls for each live clause type; no raw JSON or free-text clause entry.
- Inline clause editor: per-type fields use pickers, numeric inputs, toggles, and disabled reasons tied to the canonical clause schema.
- Covered Enemies picker: toggling scope reruns POST preview when the current draft is non-empty and structurally complete. Clauses that reference an enemy removed from `covered_enemy_participants` become invalid with `clause_target_uncovered`, highlight the offending clause, disable `Submit for Review`, and require the player to re-cover that enemy or edit/remove the clause. Scope changes must update `ignored_participants[]`, `remaining_wars[]`, and the scope badge in the next preview.
- Empty draft state: Open Settlement starts with `settlement_terms=[]`. `Submit for Review` is disabled with humanized "Author at least one clause to preview acceptance" copy. POST preview for an explicit empty authored draft returns `valid=false`, `code="empty_authored_draft"`, and no staged dialogue. Empty Back Out semantics mean zero authored clauses, not "no draft key happened to exist".
- Preview network state: while a POST settlement preview is in flight, the acceptance/preview panel shows pending state, `Submit for Review` is disabled, no editor-mode ratification control appears, and stale values are visibly marked as previous results. Preview failure preserves the last valid acceptance display with a visible stale marker and humanized "Could not preview this draft - try again" copy; it must not silently swallow the failure or show stale acceptance as current.
- Acceptance trend: after each completed clause commit after the first completed POST preview, the editor renders the previous band, current band, and humanized delta. The first completed POST preview renders current band only and no previous-band copy. If a clause edit drops the package below `acceptance.threshold`, the band transition is visible before `Submit for Review`. A structurally valid non-empty below-threshold draft may still submit into REVIEW so the player can see the blocked-review explanation and recovery routes, but the click first renders an inline warning: "This package is unlikely to be ratified. Submit anyway to see the full review?" with `Submit anyway for review` and `Continue editing`; when `losing_for_concession_baseline=true` and a material baseline is available, the warning also includes non-action guidance that the Talleyrand baseline can be used from EDIT. REVIEW then omits `confirm_settlement` and blocks mutation per SC-3 / SC-4. The warning does not appear for `near_acceptable`, `accept`, or accepted bands.
- 1080p reachability: all live clause types can be reached in a 1920x1080 viewport without controls being covered by another panel; scroll is allowed only when the focused control can be fully scrolled into view. REVIEW mode has the same constraint: header, blocker banner, covered scope, applied-clause preview, beneficiaries/ignored/remaining-war sections, hard stops/warnings, and the full action rail or labeled overflow menu must be reachable without overlap in 1920x1080.
- A clause is committed for POST preview only when all required keys for its type are populated. Clauses with missing required keys remain editor-local `in_progress`, show an inline incomplete indicator, and do not trigger POST preview until complete. Picker open/close with no selection and invalid numeric blur do not POST; they update local validation state.
- Editor-local `in_progress` clauses are not written to `world.pending_settlement_drafts` until they become complete enough for POST preview. Save/load preserves only the last completed draft package and shows a one-shot notice if a save was taken while local in-progress fields were present: "In-progress clause selections were not saved; complete a clause before saving." This avoids serializing half-formed clause payloads while keeping the loss visible.
- If a clause type's picker has zero valid options, its Add Clause control is disabled with `disabled_reason_display` instead of opening an empty picker. This applies to territory with no controlled regions, gold with no payable amount, dependency clauses with no valid target, same-side forced alliances, and liberation with no valid vassal.
- Every authored clause renders a direction tag in both editor and review mode: `Demanded` when the accepting side is burdened, `Conceded` when the player/proposer side offers value to the accepting side, and `Mutual` for `peace` or other no-material-change clauses. The tag and display prose must be consistent across the clause list, preview rows, and final review.
- Generate concession baseline: the button appears only when `losing_for_concession_baseline=true` and the deterministic baseline can produce at least one material concession beyond `peace`. It is exposed from the Action rail and anchored to the Clause controls band, replaces the current clause list only after discard-confirm if the current draft is non-empty, applies the deterministic baseline from the Concession And Treaty Conversation Contract, opens an inline Talleyrand rationale row, and immediately reruns POST preview. The button is hidden when the side-pressure predicate is false or when no material concession can be generated; the latter state renders non-action guidance copy instead of a disabled or fake concession action. A smoke fixture may disable it only through an explicit `concession_baseline_disabled=true` fixture flag recorded in the test setup.
- Required behavior tests: `test_editor_acceptance_panel_shows_band_transition_after_clause_commit`, `test_below_threshold_valid_draft_can_submit_to_blocked_review_without_ratify`, `test_below_threshold_submit_renders_inline_warning_with_two_choices`, `test_editor_covered_enemies_picker_changes_review_sections_remaining_wars_and_ignored_participants`, `test_editor_covered_enemy_picker_changes_scope_and_invalidates_referencing_clauses`, `test_open_settlement_entry_starts_with_empty_settlement_terms_and_no_previous_band_until_first_commit`, `test_submit_disabled_on_empty_settlement_terms_with_humanized_disabled_reason`, `test_post_preview_returns_empty_authored_draft_validation_error`, `test_clause_direction_tag_and_display_are_consistent`, `test_concession_baseline_button_visible_only_when_side_pressure_threshold_met`, `test_concession_baseline_button_visible_only_for_losing_side_and_pre_fills_canonical_clauses`, `test_concession_baseline_button_is_visible_at_first_paint_when_actor_is_losing_side`, `test_concession_baseline_click_time_revalidation_no_longer_eligible_renders_humanized_copy`, `test_concession_baseline_still_rejected_names_next_authoring_step_or_terminal_reason`, `test_clicking_concession_baseline_replaces_clause_list_and_re_runs_post_preview`, `test_in_progress_clause_save_load_behavior_matches_spec`, and `test_edit_mode_does_not_block_end_turn_while_review_mode_does`.

## Completion Criteria

This spec is complete only when:

- No visible settlement button is a no-op or misleading label.
- Common peace is a real term-authoring settlement system: the player can author, preview, revise/counter, and ratify concrete war-scoped terms.
- G2-Slice-1 ships at least the required first-slice live clause set: `peace`, `territory_cede`, `gold_indemnity`, and `forced_alliance`.
- Open Settlement starts with an empty local draft, disabled `Submit for Review`, no previous-band copy, and a visible Covered Enemies picker seeded by the entry path.
- Empty `settlement_terms=[]` is invalid for `Submit for Review`; POST preview returns humanized `empty_authored_draft`, and no empty package can masquerade as authored settlement.
- Covered Enemies is editable in EDIT mode, revalidates clause targets, and updates ignored participants / remaining wars / scope copy before `Submit for Review`.
- `Submit for Review` revalidates authored terms before staging and cannot drift from the preview/conflict-matrix contract.
- Unratified settlement drafts have a scoped backend storage, serialization, and end-turn discard contract keyed by `war_id`, selected target, and covered-enemy scope; drafts are not lost, silently merged across different scopes, or silently carried stale across turns.
- End-turn draft discard produces a one-shot player notice or equivalent dispatch/campaign-log signal; loading after discard does not silently erase player-authored work without explanation.
- `Ratify Settlement` cannot mutate when the displayed acceptance verdict rejects or hard stops exist.
- The ratify option is absent from `options[]` and `available_action_ids[]` whenever the backend would reject for acceptance, below-threshold score, or hard stops; blocked copy and recovery routes replace the false affordance.
- Ratification consumes acceptance `threshold` from the scorer and surfaces acceptance-changed-after-staging failures through the pinned player UX.
- Ratification and all settlement entry/editor/refusal paths follow the approved SC-4b resource-cost contract; no opener, preview, revise, back-out, stale, blocked, or failed path hides a DP/AP/gold charge.
- Proposer-side and accepting-side leader changes both use fresh rescore rather than asymmetric automatic reopen behavior.
- Accepted ratification is atomic: previewed mutations match actual mutations, and failed ratifications do not emit settlement history.
- Common peace is absent from one-to-one war surfaces.
- Settlement UI actions cannot fall back to natural-language command text.
- Settlement UI command-fallback protection is keyed by dialogue family/type, so newly added or malformed settlement action ids cannot bypass the guard by missing a local whitelist entry.
- `route_id`, `war_id`, selected target nation, and active-vs-archived `review_target` survive confirmation, revise/stale reopen, result feedback, notification, dispatch, and ledger focus.
- Every production entry path writes top-level `selected_target_nation`; first-covered-enemy fallback is diagnostic-only.
- Legacy `target_nation` is absent or exactly matches `selected_target_nation`; mismatches fail closed with humanized copy and no staged dialogue.
- Every production entry path writes or restores `covered_enemy_participants` from the entry-scope producer rules; no path silently chooses a coalition leader, alphabetic first enemy, or hidden all-enemies scope.
- Executor and staging code explicitly forward `selected_target_nation`; the field is not only a Godot-side promise.
- Settlement `route_id` values are unique enough to focus the correct row when multiple settlements occur for the same `war_id` in the same turn.
- Settlement summary and digest rows emitted by one ratification share the same staged `settlement:{war_id}:{turn}:{seq}` route id; digest rows use a marker/type tag for rendering, not a different focus namespace.
- Selected target nation survives revise/stale reopen instead of falling back to alphabetic covered enemy.
- Wizard and typed/free-text common-peace entry both reject or disambiguate multiple shared wars instead of choosing a sorted/legacy fallback.
